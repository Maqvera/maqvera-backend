# Enterprise Subscription Platform

A CORE platform — deliberately **not** under Finance (`docs/05-api/07-finance-api.md`). It governs whether a tenant can reach *any* module at all, Finance included, so it lives at the same architectural layer as authentication itself: `middleware/authenticateAccessToken.js` now enforces its own real-time decision on every authenticated request.

## Overview

"Tenant ≠ Subscription — alag concepts hain." Before this platform, `models/Tenantmodel.js` was the only real concept: a company's tenant identity with a coarse `status` (active/inactive/suspended/deleted). This platform adds the real, separate entity the spec asked for — a tenant's own relationship with this SaaS product: which plan, which billing cycle, trial/grace/suspension state, billing account, invoices — while reusing, not duplicating, the two switches that were *already* the real access-control mechanism before this platform existed:

- **`TenantModel.status`** — already checked by every `resolveDomainContext()` call in `controllers/Auth.js` (login, `GET /auth/me`, token refresh all reject a non-`"active"` tenant already).
- **`SessionModel.status`** — already checked by the refresh-token flow in the same file (a `"revoked"` session can't mint a new access token already).

This platform's real job is deciding **when** to flip those two switches for a real business reason (non-payment) — not building a second, parallel revocation mechanism next to ones that already worked. The one genuinely new piece of enforcement is closing the still-valid-access-token window (a short-lived JWT that hasn't expired yet, issued before a suspension happened) — see "Real-time enforcement" below.

## Domain Model

| Model | Purpose |
|---|---|
| `PlatformPlanModel` | The sellable plan catalog (Free/Starter/Professional/Business/Enterprise/Custom) — tenant-agnostic reference data, shared across every tenant. Real per-cycle pricing, real numeric limits (`null`/`0` = unlimited, never fabricated), a real per-plan Feature Flags `Map`. |
| `TenantSubscriptionModel` | Exactly one per tenant (unique index). The real lifecycle: `Trial → Active → PastDue → GracePeriod → Suspended`, or `→ Cancelled → Expired`. Optimistic locking (`optimisticConcurrency: true`). |
| `TenantBillingAccountModel` | The spec's own "Merchant Account" concept, **renamed to Billing Account** — see "Naming: Billing Account, not Merchant Account" below. Exactly one per tenant. |
| `SubscriptionInvoiceModel` | This platform's own invoice *to* the tenant for their subscription fee — distinct from Finance's own `InvoiceModel`, which bills the tenant's *customers*. |

`models/Tenantmodel.js` gained two audit fields (`suspendedAt`, `suspensionReason`) and real optimistic locking — `status` itself remains the actual switch, these two only explain its last flip.

## Naming: "Billing Account," not "Merchant Account"

The spec's own "Merchant Account" section describes the *tenant's* billing/payment-method profile with this SaaS platform (how a customer company pays for its own ERP license — Stripe, bank transfer, EasyPaisa, JazzCash). This is a fundamentally different concept from the "Merchant" repeatedly and deliberately dropped across every File of the Finance module refactor (Parts 45-52) — a merchant/storefront entity *within* a tenant's own business domain, which has no backing infrastructure anywhere in this codebase and still doesn't. To make sure the two are never conflated, this platform's own real concept is called **Billing Account** throughout its code and API surface, never "Merchant Account."

## Real-time enforcement (`middleware/authenticateAccessToken.js`)

Immediately after JWT verification, before permission resolution:

```
Auth (JWT valid) → Tenant Exists / Subscription Active → Permission → Execute API
```

`TenantSubscriptionService.getEnforcementBlock(tenantId)` (cached 30s via `CacheManager`, same hot-path caching discipline `resolveRolePermissions` in the same file already proves) returns:

- **`null`** — no `TenantSubscriptionModel` row exists for this tenant at all. **Every tenant that predates this platform is completely unaffected** — this is the backward-compatibility guarantee that made building this safe against the existing 470+ passing tests without touching any of them.
- **`403 SUBSCRIPTION_SUSPENDED`** — `TenantModel.status === "suspended"`. The real lockout state, only ever reached via the automatic non-payment flow (`suspendTenant`) or an admin's own explicit action.
- **`402 SUBSCRIPTION_EXPIRED`** — `TenantSubscriptionModel.status === "Expired"`, a *softer*, self-service state reached only when a tenant deliberately cancelled (`autoRenew: false`) and their paid-through period lapsed — login and the billing area stay reachable so they can see why and re-subscribe; API calls elsewhere get a clear 402.

The check **fails open** on its own error (e.g. a transient DB hiccup) — an availability bug in this platform must never itself become a reason every tenant gets locked out, matching `middleware/idempotency.js`'s own documented fail-open discipline for its store lookup.

`routes/SubscriptionPlatformRoutes.js` itself goes through the exact same `authenticateAccessToken` middleware — deliberately not double-enforced on top — so a suspended tenant's admin can still reach `GET /subscription` and `GET /invoices` to see why and pay their way back in, the same "billing area stays reachable" carve-out real SaaS platforms keep.

## Lifecycle (`services/TenantSubscriptionService.js`)

```
Company Registers → Trial Created → Subscription Created → Billing Account Linked
  → Invoice Generated → Payment Received → Subscription Activated
```

- **`startTrial`** — real per-plan `trialDays` (or the platform default), `status: "Trial"`.
- **`createSubscription`** — computes the real price from the plan's own pricing for the requested billing cycle; `status: "PastDue"` for any real (>0) price until a real payment lands, or straight to `"Active"` for a genuinely free plan — never optimistically marked Active before money has actually moved.
- **`generateInvoice`** — creates a real `SubscriptionInvoiceModel` row and sends a real reminder email (`CommunicationPlatformService`) to the Billing Account's contact.
- **`recordManualPayment`** — a human confirms money already arrived externally (bank transfer/EasyPaisa/JazzCash/cash) — never a fabricated gateway confirmation.
- **`chargeAutoDebit`** — real Stripe charge, composed from the exact same `authorize()` + `capture()` adapter methods `PaymentService` (Finance's own Payment Engine) already uses (`services/gateways/index.js` → `StripeGatewayAdapter`) — no second payment implementation. Honestly fails (never fabricates success) when the Billing Account has no real Stripe customer/payment-method on file.
- **`suspendTenant`** / **`reactivateTenant`** — the real Access Revocation mechanism: flips `TenantModel.status`, revokes every active `SessionModel` row for the tenant, flips `TenantSubscriptionModel.status`, publishes events, audits. **Never deletes any data** — exactly the spec's own "Database delete nahi karna. Kabhi nahi."

## Daily Lifecycle Sweep (`services/tenantSubscriptionScheduler.js`)

Real `node-cron` job (`PLATFORM_SUBSCRIPTION_LIFECYCLE_CRON`, default `5 0 * * *` — the spec's own "00:05"), same init pattern as the other real schedulers in `server.js`. `TenantSubscriptionService.runDailyLifecycleSweep()`, idempotent (safe to re-run mid-day — every branch checks the subscription's own current state first), every step streamed through a real MongoDB cursor and isolated per-tenant (see "Automation #1" below):

1. **Upcoming renewal** — generates the next invoice + reminder inside the configurable lead window, exactly once per period.
2. **Deliberately cancelled and lapsed** (`autoRenew: false`, period ended) → `Expired` directly — never chased through grace/reminders/suspension for a payment that was never expected.
3. **Expected to renew but unpaid** → real `GracePeriod`, even when the plan's own `gracePeriodDays` is `0` (e.g. "Free Plan 0 Days") — a zero-length grace window is immediately eligible for step 5 within the **same** sweep pass, never silently skipped into a non-suspending state.
4. **Still in grace** → at most one reminder per day (real dedupe against the last reminder actually sent).
5. **Grace period ended, still unpaid** → `enforceGracePeriodSuspensions()` (shared with Automation #1's own frequent enforcement job) → `suspendTenant` — the real "ONE TO ALL automatically" step, every tenant independently evaluated.

## Enterprise Subscription Automation Layer — Automation #1: Enterprise Subscription Scheduler

A second, real, deliberately separate initiative on top of the Subscription Platform above — this one hardens the *scheduler itself* (observability, scale, failure isolation), not the business rules it runs. Real infrastructure already existed here (the daily sweep above); this automation closes the genuine gaps: scheduler metadata/run records, batching, failure isolation, a separate faster suspension-enforcement cadence, versioned scan-lifecycle events, a monitoring dashboard, and threshold alerting.

**What was real already**: the daily sweep itself, idempotency, per-tenant independence, `publishEvent`-based domain events for every real state transition (`SubscriptionExpired`, `GracePeriodStarted`, `TenantSuspended`, `SubscriptionRenewed`, `SubscriptionArchived`).

**What's genuinely new**:

- **Batched, memory-safe scanning** — every query inside `runDailyLifecycleSweep` and the new `enforceGracePeriodSuspensions` now streams through a real MongoDB cursor (`PLATFORM_SUBSCRIPTION_SCAN_BATCH_SIZE`, default 500) instead of materializing the full matching set into memory — "Never load all companies into memory."
- **Per-tenant failure isolation** — every loop body is now individually try/caught, incrementing real `processed`/`failed` counters, so one tenant's own error (a bad plan reference, a transient DB hiccup) can never abort the rest of the batch — "Scheduler failures MUST not stop remaining batches." `runDailyLifecycleSweep`'s existing return shape is unchanged (`invoicesGenerated`, `remindersSent`, `gracePeriodsStarted`, `suspended`, `expired`, `archived` all still present, still meaning exactly what they meant before) with `processed`/`failed` added.
- **`TenantSubscriptionService.enforceGracePeriodSuspensions()`** — the daily sweep's own suspend step, extracted into its own real, shared, idempotent method.
- **`services/subscriptionSuspensionEnforcementScheduler.js`** (NEW) — a real, separate cron (`PLATFORM_SUSPENSION_ENFORCEMENT_CRON`, default every 30 minutes) that calls the exact same `enforceGracePeriodSuspensions()`, so a tenant whose grace period ends mid-afternoon is suspended within 30 minutes instead of waiting for the next 00:05 sweep — the spec's own "Suspension Enforcement Every 30 Minutes," with zero duplicated suspend logic.
- **`models/SchedulerRunModel.js` + `utils/schedulerRunTracker.js`** (NEW) — "every execution should create a run record." A real, persisted row per run (`jobId`, `status`, `startedAt`/`finishedAt`/`durationMs`, every real outcome counter) created at start (`Running`) and finalized on completion/failure, plus a real roll-up `AuditLogModel` entry (`platform.scheduler.run_completed` / `run_failed`) — "every scheduler run MUST be audited."
- **Versioned scan-lifecycle domain events** — `SubscriptionScanStarted.v1` / `SubscriptionScanCompleted.v1` / `SubscriptionScanFailed.v1` for the daily sweep, and the same pattern (`SubscriptionSuspensionEnforcementStarted/Completed/Failed.v1`) for the 30-minute job — published via the real Enterprise Event Versioning Standard (`utils/eventVersioning.js#publishVersionedEvent`), since these are genuinely new events with no existing subscriber to ever break. The spec's other named events (`SubscriptionRenewed`, `SubscriptionGraceStarted`≈`GracePeriodStarted`, `SubscriptionSuspended`≈`TenantSuspended`) already exist as real, plain `publishEvent` calls with potential real subscribers depending on their current shape — deliberately left unversioned in this pass, same precedent as the DDD Internal Domain Model standard's own "never rename an existing live event."
- **Threshold alerting** — a run that fails, runs longer than `PLATFORM_SCHEDULER_SLOW_RUN_THRESHOLD_MS` (default 15 minutes), unexpectedly drops to zero processed after a real pattern of activity, or spikes past `PLATFORM_SCHEDULER_SPIKE_MULTIPLIER`× (default 3×) its own job's recent average — all judged against that job's own real run history, never a hardcoded absolute number — logs a warning and, when `PLATFORM_SCHEDULER_OPS_ALERT_EMAIL` is configured, sends a real SMTP email (reusing Financial Reporting's own `services/delivery/EmailDeliveryAdapter.js` — no new integration).
- **Monitoring dashboard** — `GET /api/v1/platform/subscription-scheduler/dashboard` (today's renewals/suspensions — real counts from the exact existing `platform.subscription.renew`/`platform.tenant.suspend` audit actions; live grace-period company count; today's failed jobs; average runtime over the last 20 completed runs; each job's real next-scheduled-run time computed via `cron-parser` from its actual configured cron expression) and `GET /api/v1/platform/subscription-scheduler/runs` (paginated run history). Both `admin`-gated — this is platform-wide, cross-tenant operational data (a run scans every tenant), so it reuses the same tenant-scoped `admin` permission every other cross-tenant platform-operator action in this module already reuses (no separate "Platform Operator" identity exists anywhere in this codebase's auth model).

**Deliberately deferred, not faked**:

- **True horizontal multi-worker distribution** ("Scheduler → Queue → Worker Pool → Worker 1..N"). This codebase has no job-queue broker anywhere (no BullMQ/Redis Streams/RabbitMQ) — the same honest gap `utils/eventBus.js`'s own doc comment already names for `EVENT_BUS_TRANSPORT=memory` ("horizontal scaling needs a real broker adapter, not implemented yet"). The batched-cursor + per-item-isolation work above is the real, single-process-safe scalability this pass actually delivers; a genuine multi-worker queue is real, buildable follow-up once a broker is provisioned.
- **"Payment Verification Every Hour" / "Reactivation Check Every Hour"** as their own scheduled jobs. This codebase's real gateway integration (Stripe authorize+capture) is synchronous — there is no async webhook-confirmation flow for an "unverified" payment to poll for, and reactivation already happens synchronously the moment `_onPaymentReceived` fires. Building a hollow hourly poll with nothing real to check would be exactly the kind of theater this project's own standing rules forbid. The genuine future work these two map to — automatically attempting an auto-debit charge on a subscription invoice, and any real async payment-confirmation path — belongs to Automations #2 (Automatic Renewal Engine) and #3 (Payment Retry Strategy), not guessed at here.

## Enterprise Subscription Automation Layer — Automation #2: Enterprise Automatic Renewal Engine

"Jab subscription renewal date aa jaye to system automatically payment collect kare" — a real orchestrator (`services/SubscriptionRenewalEngineService.js`) on top of infrastructure that already existed and was already tested: `TenantSubscriptionService.generateInvoice` / `chargeAutoDebit` / `recordManualPayment`, none of which were rewritten. `_onPaymentReceived` was already extending a subscription's period FROM its own real `currentPeriodEnd` — "Early Renewal... Extend From Expiry Date, NOT Today's Date" was already correct before this automation existed; this engine's own new job is deciding **when** to call that chain automatically, with real idempotency, a real amount breakdown, and a real audit/event trail. Runs 10 minutes after Automation #1's own daily sweep (`PLATFORM_RENEWAL_ENGINE_CRON`, default `15 0 * * *`), same `SchedulerRunTracker` wrapper (run record/audit/alerts) Automation #1 already established.

**`models/SubscriptionRenewalModel.js`** (NEW) — one real row per (subscription, renewal period), matching the spec's own "Renewal Metadata" shape. A **unique `(subscriptionId, renewalDate)` index** is the real, DB-enforced duplicate-protection mechanism — `renewalDate` is always the subscription's real `currentPeriodEnd` at attempt time, so a second scheduler pass for a period that already reached `Renewed` genuinely can't create a second row (proven by test: a direct duplicate insert throws `E11000`), while a row that previously ended `Failed` is reused and genuinely retried on the next run, never permanently blocked.

**Renewal Calculation** ("Subscription Price → Discount → Promotional Credits → Tax → Late Fee → Final Amount"), computed in `_computeRenewalAmount`:

- **Promotional Credits — real.** When the tenant's Billing Account is linked to a real `MerchantAccountModel` (Improvement 3), the engine applies that merchant's real `MerchantWalletModel` `promotional` balance (via the existing `MerchantAccountService.debitWallet`, real recorded transaction) up to the invoice amount — genuinely debited money, not a fabricated discount. Most tenants today have no merchant link and correctly get `0` here.
- **Late Fee — real, config-driven, conditional.** `PLATFORM_LATE_FEE_FLAT_AMOUNT` / `PLATFORM_LATE_FEE_PERCENT_OF_SUBTOTAL` (both default `0`, disabled), applied only when this subscription genuinely had a prior `Failed` renewal or a prior `Overdue` invoice — never speculatively on a clean payment history.
- **Discount / Tax — honestly `0`, deliberately deferred.** No coupon/discount-code mechanism exists at this platform-billing layer (Finance's own `CouponModel` bills a *tenant's own customers*, a different domain, never reused here), and no real tax-jurisdiction engine exists for platform billing either — reusing Finance's `TaxService` would violate `SubscriptionInvoiceModel`'s own documented "never cross-referenced with Finance's models" boundary. Building a fabricated tax rate would be exactly the kind of theater this project's standing rules forbid.

**Payment attempt**: if the post-credit amount is `0`, the engine calls `recordManualPayment` with `paymentMethod: "Wallet"` (a genuine `paymentMethod` override — small, additive, backward-compatible signature extension, default still `"Manual"` for every existing caller) — zero gateway call needed. Otherwise it calls the existing `chargeAutoDebit`, which already honestly fails (never fabricates success) when no real Stripe payment method is on file. **"Secondary Method" priority is honestly not built** — only Stripe has a genuine automatic gateway integration anywhere in this codebase (the same fact `utils/platformConfig.js`'s own doc comment already establishes for the whole platform); a second automatic method would be fictional.

**Failed renewals — honest hand-off, not a stub.** "Failed renewals MUST transition to the Payment Retry Engine" (Automation #3, not yet built). Today: the invoice stays `Sent`/unpaid and the subscription's `currentPeriodEnd` never advances, so it naturally re-enters the **already-real** Automation #1 grace-period/suspension flow on the next daily sweep — a real, working fallback. Automation #3 will add real configurable multi-attempt retry scheduling on top of this same `SubscriptionRenewalModel` row.

**Domain Events** — `RenewalStarted.v1`, `RenewalInvoiceGenerated.v1`, `RenewalPaymentSucceeded.v1`, `RenewalPaymentFailed.v1`, `SubscriptionRenewed.v1` (this automation's own instance — distinct from the identically-named plain `publishEvent("SubscriptionRenewed", ...)` `_onPaymentReceived` already fires; both fire on a real successful renewal, one plain for existing subscribers, one versioned for this automation's own audit trail), all via `utils/eventVersioning.js#publishVersionedEvent`.

**Audit** — every renewal attempt (success or failure) writes one `AuditLogModel` entry, `action: "SUBSCRIPTION_RENEWAL"`, matching the spec's own literal shape (`invoiceId`, `paymentStatus: "SUCCESS"|"FAILED"`, `renewedUntil`).

**Monitoring dashboard** — `GET /api/v1/platform/renewal-engine/dashboard` (today's renewals, successful/failed/pending counts, average renewal time over the last 50 completed renewals, revenue collected today grouped by currency — real aggregates, never a guessed figure) and `GET /api/v1/platform/renewal-engine/renewals` (paginated renewal history). Both `admin`-gated, same cross-tenant platform-operator reasoning as every other dashboard endpoint in this module.

## Enterprise Subscription Automation Layer — Automation #3: Enterprise Payment Retry Strategy

"Yeh woh layer hai jo Automatic Renewal Engine aur Grace Period Engine ke beech ka bridge hai." Before this automation, a failed automatic renewal attempt (Automation #2) went straight to terminal `Failed`, honestly falling back to Automation #1's grace-period flow — a real, working, but blunt fallback. This automation makes that handoff intelligent: `services/PaymentRetryEngineService.js` now owns the entire retry-vs-exhaust decision, and Automation #2's own failure paths (`SubscriptionRenewalEngineService.processRenewal`) call into it instead of failing immediately.

**Real bridge, not a new parallel system.** `SubscriptionRenewalEngineService.completeAsFailed`/`completeAsRenewed` (renamed from `_`-prefixed private methods to intentionally public ones) are the SAME terminal-completion methods both automations now share — Automation #2 calls them directly on its own first-attempt success/immediate-exhaustion, and `PaymentRetryEngineService` calls them once ITS OWN retry sequence resolves. A lazy `import()` inside `PaymentRetryEngineService` (the same established pattern `services/PaymentService.js#allocate` already uses for `AccountsReceivableService`/`AccountsPayableService`) avoids a top-level circular dependency between the two files.

**Retry Decision Engine — real classification, honest about its own signal.** `utils/paymentRetryClassifier.js#classifyPaymentFailure` keyword-matches the ACTUAL gateway failure text (`PLATFORM_PAYMENT_RETRYABLE_FAILURE_KEYWORDS_JSON` / `PLATFORM_PAYMENT_NON_RETRYABLE_FAILURE_KEYWORDS_JSON`, both config-driven with the spec's own two lists as defaults) — the only real signal this codebase's Stripe adapter surfaces (a plain `error.message` string; no structured decline-code field exists anywhere to parse). An unrecognized reason defaults to `Retryable`, the same conservative stance real Smart-Retry systems (Stripe Billing, Chargebee) take.

**Retry Schedule** (`PLATFORM_PAYMENT_RETRY_SCHEDULE_SECONDS_JSON`, default `[86400, 259200, 604800]` = 24h/72h/7d) and **`PLATFORM_PAYMENT_RETRY_MAX_ATTEMPTS`** (default `5`, total overall attempts including the first) — both fully configurable, snapshotted onto `renewal.maxAttempts` at the first failure so a later config change never retroactively alters an in-flight sequence.

**`SubscriptionRenewalModel` extended** (not a new collection) — `status` gains a real `Retrying` state; `attemptCount`/`attempts[]` (one real entry per attempt, `{attemptNumber, status, failureReason, classification, paymentAttemptId, idempotencyKey}`) form the complete "Retry Metadata" history the spec asks for, all attempts (original + every retry) in one place; `nextRetryAt` is the real, honest, non-blocking long-horizon scheduling anchor — the exact same pattern already proven twice (`WebhookDeliveryModel`, Improvement 14; Automation #1's own suspension enforcement), never a blocking `setTimeout` across hours/days.

**Idempotency — two real layers.** (1) DB-level: `PaymentRetryEngineService.processDueRetries` atomically claims each due row (`status: Retrying -> PaymentAttempted` via `findOneAndUpdate`) before doing any work — proven by test: two "concurrent" sweeps against the same due retry process it exactly once. (2) Gateway-level: `StripeGatewayAdapter.authorize` now accepts a real, optional `idempotencyKey` (small, additive — every other existing caller omits it, behavior unchanged) passed as Stripe's own genuine request-level idempotency option; `PaymentRetryEngineService.attemptRetry` generates one deterministic key per `(renewalId, attemptNumber)`, so a crash-and-safe-re-invoke of the exact same attempt can never double-charge at Stripe even if the DB-level claim were somehow bypassed.

**Multiple Payment Methods — honest, real re-check, no fabricated methods.** Every retry attempt first re-checks real `MerchantWalletModel` Promotional-credit coverage (a merchant may have topped up between attempts) before touching the gateway again — genuinely new money each time, never assumed. "Secondary Card / Bank Account" automatic fallback stays honestly unbuilt: only Stripe has a real gateway integration anywhere in this codebase (the same fact established in Automation #2's own doc).

**Retry Isolation** — `processDueRetries` isolates each tenant's own retry in its own try/catch (same discipline as every other Automation #1/#2 sweep loop): one merchant's continuously-failing retries never block another's.

**Domain Events** — `PaymentRetryScheduled.v1`, `PaymentRetryStarted.v1`, `PaymentRetrySucceeded.v1`, `PaymentRetryFailed.v1` (via the existing `RenewalPaymentFailed.v1`/terminal path), `PaymentRetriesExhausted.v1` — all via `publishVersionedEvent`.

**Audit** — every retry attempt (success or failure) writes an `AuditLogModel` entry, `action: "PAYMENT_RETRY"`, matching the spec's own literal shape (`attempt`, `result`, `reason`).

**Scheduler & monitoring** — `services/paymentRetryEngineScheduler.js` (new, separate cron, `PLATFORM_PAYMENT_RETRY_POLL_CRON`, default every 15 minutes), wrapped in the SAME `SchedulerRunTracker` Automations #1/#2 already use. `GET /api/v1/platform/retry-engine/dashboard` (pending/today's/successful/failed retries, retry success rate, average retry time, revenue recovered — all real aggregates over `SubscriptionRenewalModel.attempts[]`) — the retry list itself reuses Automation #2's own `GET /renewal-engine/renewals?status=Retrying` rather than a duplicate endpoint. **Alerts are real reuse, not a second subsystem**: the spec's own "Retry Queue Growing / Excessive Failures -> Manual Investigation" are exactly what `SchedulerRunTracker`'s existing slow-run/zero-processed/spike alerting already covers for this job, since it wraps `processDueRetries` the same as every other scheduled job in this platform.

## Enterprise Subscription Automation Layer — Automation #4: Enterprise Grace Period Engine

"Retries fail hone ke baad merchant ko controlled grace period diya jaye, is se pehle ke Access Revocation execute ho." Real per-plan grace duration (`PlatformPlanModel.gracePeriodDays`, config fallback) already existed from Automation #1 — this automation's real job was making WHEN grace starts correct and explicit, not the duration math itself.

**The core fix: grace now genuinely begins only after retry exhaustion.** Before this automation, `runDailyLifecycleSweep`'s own step 2b started grace independently, purely from "overdue with no `gracePeriodEndsAt` set" — completely unaware of whether Automations #2/#3 were still legitimately retrying. That would have raced ahead of a subscription still mid-retry (e.g. day 3 of a 7-day final retry window), violating "Grace periods MUST begin only after retry exhaustion" outright. Now:

- **Primary trigger — real, event-driven.** `SubscriptionRenewalEngineService.completeAsFailed` (the one shared terminal-failure completion point for both Automation #2's first attempt and Automation #3's exhausted retries) calls the new `services/GracePeriodEngineService.js#startGracePeriod` the INSTANT a renewal is genuinely done retrying — not on a delay, not waiting for the next daily sweep.
- **Step 2b is now a real safety net only.** Its query gained a 1-day buffer (`currentPeriodEnd <= now - 1 day`) and, for each candidate, a real check against `SubscriptionRenewalModel` for an in-flight row (`Pending`/`InvoiceGenerated`/`PaymentAttempted`/`Retrying`) — skipped if found. Proven by test: a subscription mid-retry stays `PastDue` through a full sweep pass; a genuinely stale one (no renewal row at all — the pipeline never picked it up) is correctly recovered.

**`TenantSubscriptionModel` gains two real fields** — `graceStartedAt` (the actual "Grace Start Date," which with Automation #3 in place can now be genuinely days after `currentPeriodEnd`, never assumed to be the same moment) and `graceEndedAt` (set only on a real recovery-during-grace; a grace cycle that ends in suspension already has its own real `suspendedAt`). Both power the monitoring dashboard's real "Average Grace Duration."

**Payment during grace — already real, now explicit.** `_onPaymentReceived` (the one chokepoint every successful payment already flows through, manual or auto-debit) already unconditionally set `status: "Active"` regardless of prior state, so grace recovery was implicitly correct before this pass. Now it explicitly detects `wasInGrace`, records `graceEndedAt`, and publishes a real `GracePaymentReceived.v1` + `GRACE_PAYMENT_RECEIVED` audit entry — "Payment Received -> Verify Payment -> Renew Subscription -> Cancel Suspension -> Return ACTIVE. Automatic."

**Grace expiry -> suspension** reuses `enforceGracePeriodSuspensions` (Automations #1/#3's own shared suspend method) unchanged in its core logic, now additionally publishing `GraceExpired.v1` before the suspend call and `GraceConvertedToSuspension.v1` only once it genuinely succeeds.

**Milestone alerts — real, layered on the existing daily reminder.** `PLATFORM_GRACE_REMINDER_MILESTONE_DAYS_JSON` (default `[3, 1]`) — `GracePeriodEngineService.recordMilestoneIfDue`, called from step 3's existing daily-reminder loop, records one real, deduped `GraceReminderSent.v1` event + `GRACE_REMINDER_SENT` audit entry per milestone crossed, without sending a second duplicate email (the existing daily reminder already carries the "N days left" message).

**Merchant state machine** — the spec's own `ACTIVE -> PAYMENT_PENDING -> RETRYING -> GRACE_PERIOD -> SUSPENDED -> REACTIVATED` maps directly onto this codebase's real, pre-existing `TenantSubscriptionModel.status` values: `Active`, `PastDue`, (a `SubscriptionRenewalModel` row's own `Retrying` status — see Automation #3), `GracePeriod`, `Suspended`, and reactivation back to `Active` (real `reactivatedAt` timestamp, never a separate terminal "REACTIVATED" status, since a reactivated tenant IS simply Active again).

**Access policy during grace — stored and exposed, enforcement honestly deferred.** "Full Access + Warning | Read Only | Limited Operations... depends on company policy." `PlatformPlanModel.gracePeriodAccessPolicy` (per-plan override, `platformConfig.gracePeriodAccessPolicies` catalog, `PLATFORM_DEFAULT_GRACE_ACCESS_POLICY` platform default) is resolved and recorded on every real grace start — but nothing in this codebase yet CONSULTS it to actually restrict a `GracePeriod` tenant's requests differently from an `Active` one. That request-time enforcement is explicitly Automation #6's own job (Subscription Enforcement Middleware, not yet built); building partial enforcement inside the module that owns the grace state machine would scatter one decision across two places. The correct, real value is ready and waiting for that middleware.

**Domain Events** — `GracePeriodStarted.v1`, `GraceReminderSent.v1`, `GracePaymentReceived.v1`, `GraceExpired.v1`, `GraceConvertedToSuspension.v1`, all via `publishVersionedEvent`.

**Audit** — `GRACE_PERIOD_STARTED`, `GRACE_REMINDER_SENT`, `GRACE_PAYMENT_RECEIVED` (new); grace-driven suspension continues to use the existing `platform.tenant.suspend` audit action with its own already-real, matchable `suspendedReason` text.

## Enterprise Subscription Automation Layer — Automation #8: Enterprise Bulk Processing Engine

"Suppose 1,000 companies ki subscription ek hi date ko expire ho jaye... system stable rehna chahiye." Every prior automation's own cross-tenant sweep (Automations #1–#5) already streamed through a real MongoDB cursor with per-tenant try/catch isolation — the batching and failure-isolation halves of this automation's own ask were already real. What was genuinely missing was everything the spec's own architecture diagram names beyond that: a real bounded-concurrency worker pool (every prior sweep processed one tenant at a time, sequentially), a real distributed lock (nothing anywhere in this codebase prevented two scheduler instances from double-processing the same batch — `middleware/idempotency.js`'s own doc comment explicitly disclaims being one), real checkpoint/resume state, and a real Dead Letter Queue for a merchant whose processing keeps failing.

**Real, generic engine — `services/BulkProcessingEngineService.js`.** `runJob({ jobType, model, filter, processOne, batchSize, concurrency })` is the one real queue/batch/worker-pool/lock/checkpoint/DLQ mechanism any future mass subscription-lifecycle operation can run through, not rebuilt into each automation's own sweep:

- **Distributed lock — real, Mongo-backed, not Redis-only.** `utils/distributedLock.js` + `models/DistributedLockModel.js`. A genuinely atomic acquire (a unique-index `create()` either wins or reports a duplicate-key loss; renewing an *expired* lock goes through an atomic `deleteOne` so only one racer's re-`create()` can win, never two racers both believing they renewed the same row). Deliberately not Redis-only — `REDIS_URL` is optional throughout this codebase (`utils/cacheManager.js`'s own fallback), and a lock that silently degrades to a non-distributed in-memory `Map` when Redis is absent would be dishonest about actually preventing duplicate execution across instances; MongoDB is the one datastore every real deployment always has.
- **Real bounded-concurrency worker pool.** Genuinely concurrent, in-flight `processOne` calls — up to `PLATFORM_BULK_PROCESSING_CONCURRENCY` (default 20) at once per batch, proven by test to actually overlap (not process one item at a time) while never exceeding the configured ceiling. Honestly scoped: this is real concurrent async I/O within one Node process, not literal OS threads or separate machines — the same single-instance scope already disclosed for `utils/eventBus.js`'s in-process `EventEmitter` and `utils/resilienceEngine.js`'s in-memory circuit breaker.
- **Real checkpoint/commit.** `models/BulkProcessingJobModel.js` — one persisted row per run, its `lastCheckpointId` (the real, cursor-ordered `_id` of the last item in the last completed batch) and running counters (`processed`/`succeeded`/`failed`/`retried`/`skipped`/`deadLettered`) committed after **every** batch, not only at the end — "Processed 850, Remaining 150, Continue From 851."
- **Real per-item retry, then Dead Letter Queue.** A failing item is retried up to `PLATFORM_BULK_PROCESSING_MAX_ATTEMPTS` (default 3) times with backoff, isolated from every other item in the batch — proven by test: one deliberately-failing merchant among nine never blocks or delays the other eight. Once exhausted, it's moved to the EXISTING, shared `DeadLetterQueueModel`/`utils/resilienceEngine.js` (the Enterprise Resilience & Reliability Standard's own real DLQ) under `integration: "BulkProcessingEngine"`, never a second, parallel DLQ collection. Deliberately created directly (not via `executeResilientOperation`) — that helper's Circuit Breaker is shared per-`integration` across every call site, and tripping it after a few unrelated merchant failures would stop the whole remaining batch, directly contradicting "Baqi 999 companies continue karti rahengi."
- **Domain Events** — `BulkProcessingStarted.v1`, `MerchantProcessingStarted.v1`, `MerchantProcessingCompleted.v1`, `MerchantProcessingFailed.v1`, `BulkProcessingCompleted.v1`, all via `publishVersionedEvent`.
- **Audit** — `platform.bulk_processing.merchant_processed`/`merchant_failed` per item, matching the spec's own shape (`jobId`, `merchantId`, `result`, `processingTimeMs`, `worker`); `platform.bulk_processing.job_completed`/`job_failed` per run.

**A real, genuine bug this automation's own concurrency surfaced and fixed.** `utils/eventVersioning.js#registerEvent` (Enterprise Event Versioning Standard) raced on `findOne` → `create` when registering a brand-new `(eventName, version)` — every prior automation's sweep was sequential, so two genuinely concurrent callers publishing the same never-before-seen event name never happened until this automation's own real worker pool made it happen (`MerchantProcessingStarted.v1`, published from every worker slot). **Dead Letter Queue — real, actionable, reused infrastructure.** Browsing/listing reuses the EXISTING `GET /api/v1/resilience/dead-letters?integration=BulkProcessingEngine` and `GET /api/v1/resilience/dead-letters/:dlqId` (Resilience Standard, tenant-scoped — a tenant admin genuinely can see why their own suspension processing failed) and `POST /api/v1/resilience/dead-letters/:dlqId/permanent-failure` for giving up explicitly. ### Cross-tenant access — the one deliberate deviation from File 0's literal shape, and why

File 0's own `GET /subscriptions` (with a `tenantId` query filter) and the `{subscriptionId}` path parameters on `renew`/`suspend`/`reactivate` read, on their face, as a platform-operator surface — one actor managing *any* tenant's subscription by id. **This was not built that way.** No "Platform Operator" identity distinct from any tenant's own `admin` permission exists anywhere in this codebase's auth model (confirmed again while building this reconciliation — still true). ### `middleware/subscriptionEnforcement.js`

- **`requireFeature(featureKey)`** — router-level middleware. Because this codebase's real module boundaries already are one router file per domain, a **single `router.use(requireFeature("finance"))` line gates every endpoint in that entire file at once** — this is the real, correct shape of "retrofit every endpoint," not hundreds of individual per-route edits. Wired onto the three router files that expose a clean single `router.use(authenticateAccessToken)` mount point: `FinanceRoutes.js` (`"finance"`), `CustomerRoutes.js` (`"crm"`), `BookingRoutes.js` (`"booking"`). `VisaRoutes.js` applies `authenticateAccessToken` per-route rather than via `router.use()` (a real, pre-existing structural difference, not something this pass changed) — retrofitting it the same way would mean touching each of its many individually-authenticated routes; named here as real, valid, larger follow-up work, not attempted speculatively.
- **`requireUsageLimit(limitKey, countFn)`** — route-level middleware for a specific creation endpoint. The caller supplies its own real, already-correct count function — this middleware never counts anything itself. Wired onto `POST /api/v1/users` (`UserRoutes.js`) with `maxUsers`, counting real active `EmployeeProfileModel` rows (this endpoint's actual create target — `CreateUser` provisions an employee profile + invitation, not a `UserModel` row directly). The only other real, countable, plan-limited resource this codebase has is Storage (`maxStorageGB`) — no single existing upload endpoint aggregates a tenant's total storage usage today, so a real `maxStorageGB` wiring is named as further real, buildable follow-up rather than guessed at with a fabricated count.
- **`subscriptionResponseHeaders`** — sets `X-Tenant-Id`/`X-Subscription-Id`/`X-Plan`/`X-Feature-Version` on responses from the same three routers. `X-Company-Id`/`X-Branch-Id` from the spec's own header list are deliberately absent — Company *is* Tenant already (`X-Tenant-Id` covers it), and there is no Branch concept.

Both `requireFeature`/`requireUsageLimit` **fail open** on their own errors and are **backward-compatible by construction** — `checkFeatureAccess`/`checkUsageLimit` already default to "allowed" for any tenant with no `TenantSubscriptionModel` row, so wiring these into real, high-traffic route files changes nothing for every tenant that predates this platform. ## Enterprise Merchant & Billing Platform ("Improvement 3")

Delivered as "Tenant != Customer != Merchant != Legal Entity != Billing Account." A real, additive extension of everything above — no existing model's shape was broken, no existing lookup pattern changed. The full real hierarchy now: `MerchantAccountModel` → `TenantBillingAccountModel` (extended, not replaced) → `TenantSubscriptionModel` (unchanged) → Tenants → Users.

### The spec's own hierarchy included Branches — dropped per the standing architecture

The spec's own "Business Hierarchy" ends "...Companies → **Branches** → Users." Per the permanent §3 override, this is struck: `MerchantAccountModel`/`TenantBillingAccountModel` have no `branchId`/branch concept anywhere — the hierarchy in this codebase is `Merchant → Billing Account → Subscription → Tenants (Companies) → Users`, full stop.

### The real design decision: additive grouping, not a subscription-ownership restructure

The spec's own "ABC Holdings owns 4 companies... one subscription, not 4" is real and was built — but **not** by collapsing `TenantSubscriptionModel` into a single multi-tenant document. That would have meant restructuring the field every method in `TenantSubscriptionService.js` already queries by (`findOne({tenantId})`), which is also the exact hot-path query the **already-live, already-wired-into-every-request** enforcement middleware (`authenticateAccessToken.js`) depends on. Doing that safely, in one pass, on top of code that's already protecting real production traffic, was judged too high-risk for the value gained — and per-tenant granularity is genuinely *better* for enforcement anyway (imagine ABC Steel needs to be suspended for its own non-payment while ABC Cement stays current — a literally-merged single subscription document makes that harder, not easier).

Instead, each member tenant keeps its own full, independent, already-tested `TenantSubscriptionModel` row — real per-tenant enforcement stays completely intact — and the "one subscription" business outcome is delivered at the **invoicing layer**:

- **`MerchantAccountModel`** (new) — the real commercial identity above Tenant. `tenantIds: [String]` is the real "which companies belong to this merchant" list. Real lifecycle (`Prospect → Registered → Verified → Subscribed → Active → Suspended → Closed`) — `Subscribed` is only ever reached once a member tenant genuinely has a non-Trial `TenantSubscriptionModel` row, never assumed. "Merchant cannot login" is enforced by omission — no password/session/role field exists on this model at all.
- **`TenantBillingAccountModel`** (extended) — `merchantAccountId` (optional FK) and `additionalTenantIds` (array) together express "one merchant, this billing account, these N companies" without touching the model's own pre-existing 1:1-per-anchor-tenant shape. Added: `invoiceCurrency`, `taxAddress` (distinct from the pre-existing `billingAddress`/invoice address), `creditLimit`, `outstandingBalance`, `paymentTermsDays`, `invoiceCycle`, and typed `contacts[]` (Primary/Finance/Technical/Tax/Legal/Collection).
- **`TenantSubscriptionService.generateConsolidatedInvoice(billingAccountId)`** (new) — the real mechanism. Sums every member tenant's own real, current subscription amount into **one** `SubscriptionInvoiceModel` row (`tenantIds`/`subscriptionIds` arrays, `billingAccountId` set, `tenantId`/`subscriptionId` left null — both fields made optional for exactly this case, every existing single-tenant invoice keeps populating them as before). Real currency-mismatch guard: a member tenant whose own subscription currency doesn't match the billing account's `invoiceCurrency` is honestly skipped and reported back (`skipped: [{tenantId, currency}]`), never silently summed into the wrong total.
- **Merchant-level suspend/reactivate cascade** (`MerchantAccountService.suspendMerchant`/`reactivateMerchant`) — composes `TenantSubscriptionService`'s own already-real `suspendTenant`/`reactivateTenant` once per member tenant. A per-tenant failure is collected and reported (`failures: [{tenantId, error}]`), never allowed to silently abort the rest of the cascade — the real "ONE TO ALL automatically" the spec asks for, built from an already-tested mechanism rather than a second one.

### `MerchantWalletModel` (new)

One real wallet per merchant, 5 real balance buckets (Credit/Refund/Promotional/Adjustment/Reward), an immutable transaction log. `refundToWallet` is the real `POST /api/v1/merchant/refund` path — it credits the merchant's own Refund balance, honestly. It does **not** reverse a real Stripe/PayPal charge — this platform's own Stripe adapter only exposes `refund()` against a specific captured PaymentIntent belonging to one paid `SubscriptionInvoiceModel`, not a merchant-level concept; wiring a *real* gateway refund tied to a specific invoice is genuine, buildable follow-up work, not attempted generically here. "Cashing out" a wallet balance to a real bank account is the same kind of deferred, real gap — this wallet can only ever offset a future invoice amount, never trigger an outbound payout.

### Payment Methods

Added `ACH`, `SEPA`, `WireTransfer`, `CorporateCredit` as real labels (settling via the existing Manual path, same as every other non-Stripe method). "Visa/Mastercard/American Express/Apple Pay/Google Pay" from the spec's own list are deliberately **not** separate top-level methods — they're real card brands/wallets Stripe's own `PaymentMethod` object already distinguishes once a tenant is on `"Stripe"`; modeling them as 5 more parallel gateway entries would fabricate 5 integrations this codebase doesn't have.

### New API surface (`routes/MerchantPlatformRoutes.js`, mounted at `/api/v1`)

`POST/GET /merchants`, `GET /merchants/:id`, `POST /merchants/:id/verify`, `POST /merchants/:id/join` (links the **caller's own** tenant only — never an arbitrary tenantId), `POST /merchants/:id/suspend|reactivate`, `GET /merchants/:id/wallet`, `GET/POST /billing-accounts`, `POST /billing-invoices` (the real consolidation endpoint), `POST /payment-methods`, `POST /wallets`, `POST /merchant/refund`, `GET /billing-history`. Same cross-tenant-safety discipline as every prior Improvement: every handler that resolves a merchant by id verifies the caller's own tenant is actually a member (`assertOwnMerchant`) before acting — a foreign merchant id 404s, never 403s, so its existence is never confirmed either.

### Domain events
