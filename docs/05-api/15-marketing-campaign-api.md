# Marketing Campaign API

PRD "CRM Feature Map by Phase" Phase 2 module 20 (part). All routes live under `routes/MarketingCampaignRoutes.js`, mounted at `/api/v1/campaigns`, and require `authenticateAccessToken` — tenant scope is always `getAccessScope(req)`. Permission keys: `campaign.read`, `campaign.create`, `campaign.manage` (or `admin`).

Deliberately distinct from `CollectionCampaignModel`/`CollectionCampaignController` (finance/debt-collection campaigns targeting overdue payments — a different domain) and from `SmsPlatformService.createBulkCampaign` (an existing SMS-only bulk-send tool). This is the cross-channel (Email/SMS/WhatsApp) customer-segment campaign the PRD's Marketing Campaign System line item asks for — a thin orchestration layer over already-built infrastructure, never a new send/provider path:

- Templates come from the existing `CommunicationTemplateModel` (`channel` must match the campaign's own channel exactly, and the template must be `Active` — `CommunicationTemplateService.getPublishedTemplateForSend` is reused, not re-implemented).
- The actual send fans out one call per recipient to `EmailPlatformService.sendEmail` / `SmsPlatformService.sendSms` / `WhatsAppPlatformService.sendWhatsApp` (`sourceModule: "MarketingCampaign"`), the same services every other module in this codebase already sends through.
- Segments are resolved with the exact same filter shape `GET /customers` (`ListCustomers`) already accepts (`customerType`, `category`, `status`, `assignedTo`, `countryId`, `cityId`, `createdAfter`, `createdBefore`) — never a client-supplied raw Mongo query.

## Endpoints

- `POST /api/v1/campaigns` — `{name, channel: "Email"|"SMS"|"WhatsApp", templateId, segmentFilter?, scheduledAt?}`. Resolves `segmentFilter` against `CustomerModel` (tenant-scoped, `status != archived`, plus the channel's required contact field present — `email` for Email, `phone` for SMS/WhatsApp), and snapshots the result into one `MarketingCampaignRecipientModel` row per matching customer (`status: "pending"`) — a later customer-data change never silently changes who a sent campaign went to. 400s if the template's own `channel` doesn't match the campaign's declared `channel`. Requires `campaign.create` (or `campaign.manage`/`admin`).
- `GET /api/v1/campaigns?status=&channel=` — list, tenant-scoped. Requires `campaign.read` (or higher).
- `GET /api/v1/campaigns/{campaignId}` — detail. Requires `campaign.read` (or higher).
- `POST /api/v1/campaigns/{campaignId}/send` — only from `status: "draft"` or `"scheduled"`; 400s otherwise (a campaign can never be re-sent). Loops every `pending` recipient, attempts the real send, and records each outcome on that recipient's own row (`sent`/`failed` + `trackingId`/`error`) — **one recipient's failure (bad email, no WhatsApp conversation window, provider rejection) never aborts the rest of the fan-out**. Sets `status: "sent"` and `sentCount`/`failedCount` once every recipient has been attempted, even if some failed. Requires `campaign.manage`.
- `GET /api/v1/campaigns/{campaignId}/analytics` — `{campaignId, status, recipientCount, byStatus: {pending, sent, delivered, opened, clicked, failed}}`, aggregated live off `MarketingCampaignRecipientModel` (no pre-built per-campaign rollup exists in `CommunicationAnalyticsEngine` today — this is its own small aggregation). `delivered`/`opened`/`clicked` stay `0` until a future webhook/tracking-pixel integration updates recipient rows past `sent` — this endpoint reports what's tracked today honestly rather than fabricating engagement numbers. Requires `campaign.read` (or higher).
