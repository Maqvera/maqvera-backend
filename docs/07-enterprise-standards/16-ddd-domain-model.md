# Enterprise Domain-Driven Design (DDD) Internal Domain Model Standard

**Status: ✔ Done** — this codebase had no `domain/` layer at all before this pass: every business rule lived inline inside `services/*.js`, invoked directly against Mongoose models. This standard introduces the real, shared DDD building blocks (`domain/shared/`) and proves every one of them, for real, on one flagship module — **Payment** (the same flagship `POST /payments` endpoint Improvement 15 documented) — the richest real domain already in this codebase and the spec's own worked example. Additive-first, with one deliberate, carefully-scoped, behavior-preserving refactor of `services/PaymentService.js` itself (see "The one real refactor" below).

## Why Payment, and why not "all 16+ modules at once"

Hand-building a full Aggregate/Entity/Value-Object/Repository/Domain-Service/Policy/Specification/Factory/Domain-Event set for every business module (Invoice, Merchant, Booking, Visa, Subscription, Journal, Settlement, ...) in one pass would be thousands of lines built against business rules this pass didn't have time to re-derive and verify line-by-line against each service's existing behavior — exactly the kind of disproportionate, error-prone, "looks complete but isn't verified" work this whole hardening phase has consistently avoided (see Improvement 15's own identical scope call on OpenAPI path coverage). Instead: one module gets the full, real, *wired-into-production* treatment, proving every building block actually works against this codebase's real data and real tests — not a toy example — and the pattern is now real and ready to repeat.

## The shared building blocks (`domain/shared/`)

- **`Entity.js`** — identity-based equality (`equals()` compares ids, not fields); throws on construction without an id.
- **`ValueObject.js`** — structural equality; genuinely immutable via `Object.freeze()` on both the instance and its props (not just "immutable by convention" — mutating a frozen value object's props throws in strict mode, verified by test).
- **`AggregateRoot.js`** — extends `Entity`; `raiseDomainEvent(name, payload)` / `pullDomainEvents()` implement the standard "collect then dispatch" pattern.
- **`Specification.js`** — `isSatisfiedBy(candidate)` plus real `.and()` / `.or()` / `.not()` composition, the literal "instead of if/if/if/if/if/if" the spec asks for.

## The Payment module's Internal Domain Model (`domain/payment/`)

| Building block | File | Real content |
|---|---|---|
| Aggregate Root | `PaymentAggregate.js` | Wraps a persisted Payment (Mongoose document or plain object) **by reference** — `apply*` methods mutate the wrapped state in place, so the existing `payment.save()` call after an `apply*` call persists exactly what the aggregate decided. Owns `applyRefund`, `applyVoid`, `applyCapture`, `applySettle`, `applyAllocation`, each raising a real domain event. |
| Entities | `entities/PaymentAllocation.js` | Mirrors the real `PaymentAllocationSchema` sub-document in `models/PaymentModel.js` — identity, not addressed directly, owned by the aggregate. |
| Value Objects | `valueObjects/Money.js`, `PaymentMethod.js`, `ReferenceNumber.js` | `Money` — immutable arithmetic (`add`/`subtract`), currency-mismatch guard, the exact same 2dp rounding `roundCurrency` has always used. `PaymentMethod` pairs a method with its resolved gateway. `ReferenceNumber` wraps the server-generated `paymentNumber`. |
| Repository | `PaymentRepository.js` | `findById` / `save` / `list` — pure persistence, delegates straight to `PaymentModel`, no business logic. |
| Domain Service | `services/PaymentFraudDomainService.js` | `computeFraudRiskScore` / `deriveFraudStatus` — rule-based (not AI) fraud signal spanning multiple pre-gathered inputs, the canonical DDD "Domain Service" case (behavior that doesn't belong to any single entity). |
| Domain Policies | `policies/GatewayRoutingPolicy.js`, `policies/RefundPolicy.js` | `resolveGateway` — which gateway a payment method actually routes to. `RefundPolicy` — "a refund can only ever consume the currently-unallocated portion; already-allocated funds must be reversed via their own target's mechanism," the exact rule `PaymentService.refund` has always enforced. |
| Specifications | `specifications/Can{Refund,Void,Capture,Settle,Allocate}Specification.js` | One file per business eligibility rule, each also exporting the underlying pure status predicate (`isPaymentRefundable`, etc.) as the one canonical definition. |
| Factory | `PaymentFactory.js` | Builds the invariant-satisfying initial state for a brand-new payment (rounds the amount via `Money`, resolves the gateway via `GatewayRoutingPolicy`) — takes an already-generated `paymentNumber` rather than touching the database itself, keeping it a pure, zero-I/O Domain Layer object. |
| Domain Events | Raised inside `PaymentAggregate` | `PaymentRefunded.v1`, `PaymentVoided.v1`, `PaymentCaptured.v1`, `PaymentSettled.v1`, `PaymentAllocated.v1` — versioned names, collected via `pullDomainEvents()`. See "Domain events vs. the existing event bus" below for why these are NOT (yet) wired into `publishEvent`. |

## The one real refactor: `services/PaymentService.js`

Moving business rules into a domain layer is meaningless if the service layer keeps re-implementing them inline — so `PaymentService.refund`, `.void`, `.capturePayment`, `.markSettled`, and `.consumeUnallocatedAmount` were refactored to construct a `PaymentAggregate.fromPersistence(payment)` and call its `can*`/`apply*` methods instead of the previous inline `if (!isPaymentRefundable(status)) throw ...` + hand-rolled arithmetic. `getPaymentById` now delegates to `PaymentRepository.findById`. The pure predicate functions (`resolveGateway`, `computeFraudRiskScore`, `deriveFraudStatus`, `isPaymentAllocatable`, `isPaymentVoidable`, `isPaymentRefundable`, `isPaymentSettleable`, `isPaymentCapturable`) moved to their canonical domain-layer homes, with `PaymentService.js` importing and **re-exporting the exact same function references** — every existing import site (`services/PaymentIntentService.js`, `services/CustomerCollectionService.js`, `services/SettlementService.js`, `services/RefundService.js`, `tests/paymentService.test.js`) keeps working with zero changes, verified by test (`reExportedResolveGateway === resolveGateway`, same reference, not a re-implementation that could drift).

**This is a genuinely behavior-preserving refactor, not a rewrite**: `createPayment` (the multi-branch gateway-authorize-then-capture orchestration) and `allocate`'s AR/AP delegation were deliberately left untouched — too much branching, blast radius, and cross-service dependency to safely fold into the aggregate in one pass. Verified via the full existing test suite, unmodified: `tests/paymentService.test.js` (12/12), plus every live-MongoDB test that exercises the refactored methods end-to-end — `tests/refundService.test.js`, `tests/settlementService.test.js`, `tests/accountsReceivableService.test.js`, `tests/accountsPayableService.test.js`, `tests/walletService.test.js`, `tests/customerPaymentIntent.test.js`, `tests/customerPaymentCollect.test.js`, `tests/paymentIntentService.test.js`, `tests/walletAndSubscriptionIntegration.test.js` — 44/44 passing, unchanged.

## Domain events vs. the existing event bus

`PaymentAggregate` raises real, versioned domain events (`PaymentRefunded.v1`, etc.) into its own internal queue, testable via `pullDomainEvents()`. This pass deliberately does **not** wire that queue into `utils/eventBus.js#publishEvent` or `utils/eventVersioning.js#publishVersionedEvent`. This codebase's existing plain event names (`"PaymentCaptured"`, `"PaymentRefunded"`, ...) already have real subscribers — `WebhookService`, `BankAccountService`, AR/AP — depending on their exact current name and flat payload shape, and Improvement 7 (Event Versioning) already established the precedent that an existing live call site is never silently renamed or restructured. Dual-publishing here without a real consumer for the versioned form would just be event-bus noise. See "Adoption" for the real follow-up path.

## Real test coverage (`tests/dddPaymentDomainModel.test.js`)

15 tests, all passing, no MongoDB dependency (pure/static domain logic): `Entity`/`ValueObject`/`AggregateRoot`/`Specification` shared building blocks; `Money` arithmetic and rounding; `PaymentMethod`/`ReferenceNumber`/`PaymentAllocation` invariants; `GatewayRoutingPolicy`/`RefundPolicy` business rules; every Specification's predicate locked against the exact statuses `PaymentService.js` has always used; `PaymentFraudDomainService` output parity; `PaymentAggregate` refund/void/capture state transitions (including the two-step partial-refund-then-full-refund sequence reaching `"Refunded"`); `PaymentFactory` building an invariant-satisfying initial state; `PaymentRepository.save` delegating to the document's own `save()`; and the re-export identity check proving `services/PaymentService.js` didn't fork the logic. Plus the full existing Payment-dependent suite (44 tests across 9 files, listed above) re-run unmodified and passing, proving the refactor didn't change observable behavior.

## Adoption

Real, deliberate, incremental follow-up — not attempted in this pass:

- **Every other business module** (Invoice, Merchant, Subscription, Booking, Visa, Journal, Settlement, AR/AP, ...) still has its business logic inline in its service layer. Payment proves the pattern; applying it module-by-module is the real remaining work, sized the same way Improvement 15 sized "document the remaining ~250 Finance endpoints."
- **`createPayment` and `allocate`'s AR/AP delegation** were not folded into `PaymentAggregate` — a genuinely larger refactor (multi-branch gateway orchestration, cross-service calls) deferred to reduce this pass's blast radius.
- **Dual-publishing `PaymentAggregate`'s versioned domain events onto the real event bus** once a genuine new consumer needs the `EnterpriseEventEnvelope` shape (Improvement 7/15) rather than the existing flat payload.
- **The "Internal Domain Model" section required in every module's own `.md` file** — added to `docs/05-api/07-finance-api.md`'s Payment section as the flagship; extending it to every other module doc is the same kind of incremental, honest follow-up as Improvement 15's JSDoc coverage gap.
