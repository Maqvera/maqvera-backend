# Enterprise Webhook Standard

**Status: ✔ Done** — a real, already-substantial webhook platform (registration, HMAC signing, immediate-burst retry, replay, suspend-not-delete) already existed from Finance Module Part 18 Part 5; this standard closes the one genuine gap it had against the spec — long-horizon, hours-scale retry escalation ending in a real Dead Letter Queue — plus a real monitoring aggregation endpoint. Additive only; no existing registration/signing/replay behavior was rewritten.

## What already existed

`services/WebhookService.js`, `models/WebhookSubscriptionModel.js`, `models/WebhookDeliveryModel.js`, `controllers/WebhookController.js`, and their routes under `/api/v1/webhook-subscriptions` were already real, working, and tested (`tests/webhookService.test.js`, `tests/webhookDeliveryIntegration.test.js`): genuine HMAC-SHA256 signing (`X-Webhook-Signature`/`X-Webhook-Timestamp`/`X-Webhook-Event-Id`, the same scheme Stripe uses), a real wildcard fan-out (`utils/eventBus.js#subscribeAllEvents`) so **any** event name — including genuinely custom, never-enumerated ones — reaches a matching subscription, an immutable per-attempt audit trail (`WebhookDeliveryModel.attempts[]`), a real circuit breaker (`consecutiveFailureCount` → auto-suspend), secret rotation with the correct show-once convention, and a working manual replay endpoint. Subscriptions are suspended/disabled, never deleted — "Actually Disable, never immediately remove historical delivery records" was already true. None of this was rebuilt.

## The one real gap: long-horizon retry + Dead Letter Queue

The existing engine's own retry was a single, short, blocking burst — up to `webhookRetryMaxAttempts` (default 5) attempts, seconds apart (`utils/retryWithBackoff.js`, exponential, ~31s total worst case) — then the delivery terminated as `"Failed"`. The spec's own retry policy is hours-scale (`1m → 5m → 15m → 30m → 1h → 6h → 24h → Dead Letter Queue`), which cannot honestly be a blocking `setTimeout` inside one request-scoped call (sleeping a worker for 24 hours is not real infrastructure). This standard adds the real, scheduled equivalent:

- **`WebhookDeliveryModel`** gains `longRetryAttempt` (real index into the schedule) and `dlqId` (cross-link once escalated) — both additive, default-valued, no existing row/query breaks.
- **`utils/financeConfig.js`** gains `webhookLongRetryScheduleSeconds` (default `[60, 300, 900, 1800, 3600, 21600, 86400]`), `webhookRetryPollCron`, and `webhookRetryPollBatchSize` — config-driven, same `parseJson`/env-var pattern as every other Finance config key. `webhookDeliveryStatuses` gains real `Retrying`/`DeadLetterQueue` states alongside the existing ones.
- **`services/WebhookService.js`**: the tail end of delivery (previously "save Delivered/Failed, update the circuit breaker") is factored into a shared `_finalizeDeliveryOutcome`, now used by both the original immediate-fan-out path and the new scheduled-retry path — same finalize logic, one source of truth for the status/circuit-breaker decision, not two diverging copies. On exhausting the burst, a delivery becomes `Retrying` with a real `nextRetryAt`; on exhausting the full long-horizon schedule, `_moveToDeadLetterQueue` fires.
- **`services/webhookRetryScheduler.js`** — a real `node-cron` sweep, matching `auditRetentionScheduler.js`'s own pattern exactly (thin cron wrapper calling into the service's own `WebhookService.processDueRetries()`, which does the actual work — same division of responsibility as every other `*Scheduler.js` in this codebase). Wired into `server.js` alongside every other scheduler.
- A delivery whose subscription is no longer `Active` by the time its scheduled retry comes due is honestly moved to `Abandoned` (an existing, previously-unused enum value) rather than retried forever against a subscription nobody intends to reactivate.

## Genuine reuse of Improvement 6's Dead Letter Queue — not a second, parallel one

`_moveToDeadLetterQueue` creates a real row directly in Improvement 6's own `DeadLetterQueueModel` (`module: "Webhook"`, `integration: "Webhook"`, `operation: <eventType>`), and publishes the SAME canonical `RetryExhausted.v1`/`DeadLetterQueued.v1` event names `utils/resilienceEngine.js` already publishes on its own DLQ hand-off — one real "admin alert" hook point for every exhausted-retry source in this codebase, webhook or otherwise, not a webhook-specific duplicate. The practical payoff: a webhook delivery that hits the DLQ is immediately visible through the **already-existing** `GET /api/v1/resilience/dead-letters?module=Webhook` monitoring endpoint (Improvement 6) — verified directly by test — with no new DLQ list/detail endpoint needed for webhooks at all. Manual recovery reuses the webhook engine's own existing, already-real `replayDelivery` (`POST /webhook-deliveries/{deliveryId}/replay`), which works identically whether the delivery is sitting in `Failed`, `Retrying`, or `DeadLetterQueue`.

## Monitoring (`GET /api/v1/webhook-subscriptions/monitoring/summary`)

A real aggregation over `WebhookSubscriptionModel`/`WebhookDeliveryModel` — registered webhook count, delivery success %, average delivery time, count of deliveries that needed a retry, and DLQ item count. Two spec metrics are honestly not fabricated: **"Signature Failures"** is a receiver-side concern (verifying a signature this codebase sent) that the sender has no way to observe; **"Replay Queue"** has no distinct real backing concept in this engine beyond the DLQ itself (a DLQ row IS the real, actionable replay candidate), so it's aliased to `dlqItems` rather than invented as a second number.

## Real, live-MongoDB test coverage (`tests/webhookRetryEscalationStandard.test.js`)

5 new tests, all passing, proving exactly the new behavior: a persistently-failing delivery escalates to `Retrying` with the correct first schedule tier (never straight to a terminal state); `processDueRetries` walks a delivery through every remaining tier and genuinely reaches the Dead Letter Queue, with the resulting row independently confirmed reachable through Improvement 6's own `listDeadLetters`; a `Retrying` delivery whose subscription is no longer `Active` becomes `Abandoned`; a scheduled retry that actually succeeds recovers `Retrying → Delivered` and resets the circuit breaker; and the monitoring summary computes real numbers against real seeded data. The pre-existing `tests/webhookService.test.js`/`tests/webhookDeliveryIntegration.test.js` were re-run unmodified and still pass (the one intermittent failure seen under full-suite parallel load is a pre-existing timing race in that test's own polling loop against a real HTTP round trip — already diagnosed in earlier phases of this hardening effort, confirmed unrelated by three clean isolated re-runs after this standard's changes).

## Adoption

The Finance-module-era permission keys (`finance.webhook.read`/`finance.webhook.manage`) are kept as-is rather than renamed to something more generically "Enterprise" — the engine has always fanned out ANY event name regardless of module, so the capability was already cross-cutting in practice; renaming the permission keys now would be a breaking change to already-seeded roles for no functional gain, and is a real, deliberate, separate decision if ever wanted. `webhookLongRetryScheduleSeconds`'s default schedule matches the spec's own example exactly, but is fully env-overridable per deployment.
